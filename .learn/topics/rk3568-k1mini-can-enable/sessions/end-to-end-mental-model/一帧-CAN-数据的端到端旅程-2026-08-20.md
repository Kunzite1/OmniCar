## Positioning

这是整张知识地图的入口：先看懂一帧数据怎样穿过应用程序、Linux、RK3568、收发器、物理总线和 STM32，后面的设备树与镜像修改才知道自己究竟在“接通”哪一段。

## Core Mechanism

在 OmniCar 中，一帧 CAN 数据不是由一个程序直接送到另一个程序，而是依次经过多层软硬件：

```text
K1 Mini 用户程序
  ↓ SocketCAN 套接字
Linux CAN 网络层
  ↓ Rockchip CAN 驱动
RK3568 CAN 控制器
  ↓ TXD 数字信号
K1 Mini CAN 收发器
  ↓ CAN_H / CAN_L 差分电信号
CAN 物理总线
  ↓
STM32 CAN 收发器
  ↓ RXD 数字信号
STM32F407 CAN1 控制器
  ↓ 中断与 FreeRTOS 队列
OmniCar 指令处理任务
```

反方向发送时，同一条链路倒过来走。Linux 把真实 CAN 控制器注册为网络接口，应用通过 SocketCAN 使用它；它不是串口字符设备。Linux 内核把发送方向概括为“套接字缓冲区交给 CAN 控制器”，接收方向则相反，详见 [Linux 内核 SocketCAN 文档](https://docs.kernel.org/networking/can.html)。

### 1. 一帧数据长什么样

本项目约定使用经典 CAN 标准数据帧：

- 标准标识符是 11 位，范围为 `0x000`～`0x7FF`。
- 数据长度 DLC 为 0～8 字节。
- 总线速率为 500 kbit/s；所有参与通信的节点必须使用兼容的位时序。
- 本项目关闭 CAN FD，发送的是经典 CAN 帧。
- CAN ID 主要表示报文含义和仲裁优先级，不是类似 IP 地址的“收件人地址”。CAN 是广播总线，所有正常连接的节点都能在物理层看到帧，再由控制器过滤器和软件决定是否接收、处理。

本项目使用三个关键 ID：`0x101` 是 STM32 发给上位机的心跳，`0x2FF` 是 K1 Mini 发给 STM32 的测试请求，`0x2FE` 是 STM32 返回的测试应答。

### 2. 真正发送前必须具备的条件

一帧数据能够上总线，需要下面各层同时成立：

1. K1 Mini 的内核包含 Rockchip CAN 驱动。
2. 运行设备树把 RK3568 的 CAN1 节点设为 `okay`，选择 `can1m0_pins`，并禁用占用相同 3、5 号物理引脚的 I2C3 M0。
3. 驱动成功探测控制器并注册 SocketCAN 接口。本项目虽然启用的是 SoC 的 CAN1，但它是系统中第一个注册的 CAN 接口，所以显示为 `can0`。
4. `can0` 被配置为经典 CAN 500 kbit/s 并置为 `UP`。`ip link` 只能配置已经由驱动注册的接口；它不能凭空启用设备树中被禁用的控制器。
5. K1 Mini 和 STM32 各自经过 CAN 收发器连接，CAN_H 对 CAN_H、CAN_L 对 CAN_L、两板共地，总线两端各有 120 Ω 终端电阻。
6. STM32 的 CAN1 也以 500 kbit/s 正常启动。当前固件使用 PD0/PD1、标准数据帧，并把接收过滤器设置为全接收。

这个项目定制镜像的目的，就是补齐第 2 项，从而让第 3 项发生。因为 K1 Mini 的 U-Boot 最终可能从 `resource.img` 选择硬件 DTB，所以脚本不仅修改 FIT 基础 DTB，还同步修改 13 份硬件 DTB；只改基础 DTB，启动后仍可能看不到 `can0`。

### 3. K1 Mini 发送 `0x2FF` 时发生什么

执行：

```text
cansend can0 2FF#A1B2C3D4
```

其含义是：在 `can0` 上发送一帧 11 位标准 ID 为 `0x2FF`、DLC 为 4、数据为 `A1 B2 C3 D4` 的经典 CAN 数据帧。

完整旅程如下：

1. `cansend` 打开并使用 SocketCAN RAW 套接字，把 CAN ID、长度和数据交给 Linux 网络层。
2. Linux 把帧放入网络发送队列，Rockchip CAN 驱动再把它交给 RK3568 CAN 控制器。命令成功返回首先说明本机软件接受了发送请求，并不等于 STM32 应用已经处理。
3. RK3568 CAN 控制器把帧编码成 CAN 位流，通过 TXD 送给外部 CAN 收发器。
4. 收发器把单端数字信号转换成 CAN_H、CAN_L 上的差分电信号。收发器负责电气转换，不理解 `0x2FF` 的业务含义。
5. 如果多个节点同时发送，它们会逐位仲裁。对于本项目使用的 11 位标准数据帧，ID 数值较小的帧通常优先；更完整地说，仲裁还包含 RTR、IDE 等相关位，所以“数字越小优先级越高”只适用于帧格式条件相同的常见情况。
6. STM32 一侧的收发器把差分信号还原为 RXD，CAN1 控制器检查帧格式、位填充和 CRC。正确接收帧的其他活动节点会在 ACK 槽发送确认；如果发送端没有采样到 ACK，就会报告 ACK 错误。CAN 帧结构和 ACK 规则可参考 [CiA 的经典 CAN 帧说明](https://can-cia.org/can-knowledge/can-cc)。ACK 只证明至少一个节点在数据链路层正确收到帧，不证明指定应用已经处理它。
7. STM32 当前过滤器全部接收并送入 FIFO0；CAN1 RX0 中断调用 HAL，HAL 回调取出 ID、DLC 和数据，再从中断上下文写入 FreeRTOS 队列。
8. `canTask` 从队列取帧，协议层把 `0x2FF` 识别为 echo 请求，然后发送 ID 为 `0x2FE` 的应答。
9. `0x2FE` 沿相反方向通过 STM32 CAN1、STM32 收发器、物理总线、K1 Mini 收发器、RK3568 控制器、Linux 驱动和 SocketCAN，最终被 `candump` 显示。

对于示例的 4 字节请求，当前固件固定返回 8 字节：

```text
2FE#A1B2C3D400000000
```

前 4 字节被回显，其余位置由 0 补齐。当前实现还有一个需要知道的边界：请求长度为 1～7 字节时都会回显已有字节；若请求恰好为 8 字节，代码只保留前 7 字节，最后一个字节会被丢弃。这是当前源码的实际行为，不应把它误认为通用 CAN 规则。

### 4. STM32 的 `0x101` 心跳怎样到达 `candump`

STM32 的默认任务每 1000 ms 调用一次心跳发送函数。协议层构造一个 8 字节帧：第 0 字节是不断递增并自然回绕的序号，第 1～3 字节是固件版本，其余字节当前为 0。随后 BSP 把它作为标准数据帧 `0x101` 写入 STM32 CAN1 发送邮箱。

帧经过 STM32 收发器和物理总线到达 K1 Mini。RK3568 CAN 控制器接收后，驱动把它交给 Linux CAN 网络层，绑定 `can0` 的 `candump` RAW 套接字最终读到并打印它。

所以，`candump` 每秒看见一次序号递增的 `0x101`，证明的不只是某一个函数运行了，而是下面整条链路至少在这个方向已经贯通：

```text
STM32 应用 → STM32 CAN1 → 两端收发器与总线 → RK3568 CAN → Linux 驱动 → SocketCAN → candump
```

### 5. 怎样判断“真的端到端成功”

仅看到自己发送的 `0x2FF` 还不够。SocketCAN 默认支持本地回环，监听程序可能看到本机刚提交的发送帧；这主要方便同一主机上的多个程序观察总线流量。

证据强度从弱到强大致是：

1. `can0` 存在：设备树和驱动探测大概率成功。
2. `can0` 能置为 `UP`：接口和位时序配置被驱动接受。
3. TX 计数增加：Linux 已尝试发送，但不保证远端应用收到。
4. 总线没有持续 ACK error、bus-error 或 bus-off：物理层和位时序更可能正确。
5. 收到 STM32 主动发送的 `0x101`：STM32 到 K1 Mini 的方向贯通。
6. 发送 `0x2FF` 后收到 STM32 生成的 `0x2FE`：K1 Mini 到 STM32、STM32 软件处理、以及返回方向都贯通，这是本项目最完整的端到端证据。

如果没有 ACK，CAN 控制器会记录 ACK 错误；是否自动重发取决于控制器与驱动配置。当前 STM32 工程明确关闭了自动重传，因此不能笼统假设每一端都会无限重试。

## Analogy

可以把这条链路想成一间所有人都能听见的会议室：

- `cansend` 是准备发言的人。
- SocketCAN 是统一的发言登记台。
- Rockchip 驱动是把发言稿交给硬件的人。
- CAN 控制器负责按严格格式、时序和优先级发言。
- 收发器像麦克风和扬声器之间的电气转换器。
- CAN_H、CAN_L 是会议室里共享的声音通道。
- STM32 CAN1 先检查“声音”是否符合规则，再把内容放入 FreeRTOS 收件队列。
- `canTask` 读到 `0x2FF` 后，用 `0x2FE` 回答。

这个类比适合说明“分层”和“广播”，但不覆盖真实 CAN 的差分电压、逐位无损仲裁、CRC、位填充、错误帧和精确采样时序；这些工作由 CAN 控制器和收发器按协议完成，并不是人类会议真的具有的机制。

```sh
# 📁 资料/K1MINI开启CAN设备.md:108-129

# 1. 配置已经由驱动注册出来的 can0
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 500000 fd off restart-ms 100
sudo ip link set can0 up

# 2. 终端 A：监听所有到达 can0 的帧
candump -L can0

# 3. 终端 B：发出项目约定的 echo 请求
cansend can0 2FF#A1B2C3D4

# 4. 终端 A 应看到 STM32 生成的响应
# 2FE#A1B2C3D400000000
```

逐步对应源码：

1. STM32 启动时，`BSP_CAN_Init()` 配置全接收过滤器、创建队列、开启 FIFO0 消息中断并启动 CAN1。
2. `App_Loop()` 每秒调用 `CanProto_SendHeartbeat()`，因此终端 A 应持续看到 `0x101`。
3. `cansend` 发出的 `0x2FF` 到达 STM32 后，HAL 接收回调把帧写进 FreeRTOS 队列。
4. `App_CmdHandler_Task()` 阻塞等待队列；解析出 `CANPROTO_MSG_ECHO_REQ` 后调用 `CanProto_SendEchoRsp()`。
5. `CanProto_SendEchoRsp()` 构造固定 8 字节的 `0x2FE`，通过 `BSP_CAN_Send()` 放入 STM32 CAN1 发送邮箱。
6. 终端 A 看到 `0x2FE`，表示请求和响应两条路径都已完成。

## Common Misconceptions

1. **“安装 `can-utils` 就会出现 `can0`。”** 不会。`can-utils` 只是用户态工具；真实接口必须由设备树、内核驱动和控制器共同注册。
2. **“启用 RK3568 的 CAN1，接口一定叫 `can1`。”** 不一定。Linux 通常按注册顺序命名；本项目的 CAN1 实际显示为 `can0`。
3. **“`ip link set can0 up` 会启用被设备树禁用的硬件。”** 不会。如果根本没有 `can0`，应先检查运行设备树和驱动探测。
4. **“开发板的 TX/RX 可以直接接 CAN_H/CAN_L。”** 不可以。TXD/RXD 是控制器逻辑信号，CAN_H/CAN_L 是差分总线信号，中间必须有合适的 CAN 收发器。
5. **“看到自己发出的 `0x2FF` 就证明 STM32 收到了。”** 不成立，它可能只是 SocketCAN 本地回环；收到 STM32 生成的 `0x2FE` 才是应用层往返证据。
6. **“CAN ID 是接收节点地址。”** 不准确。CAN 帧在总线上广播，ID用于仲裁和描述报文含义；每个节点自行过滤和解释。
7. **“两端都配置 500 kbit/s 就一定能通信。”** 还必须满足引脚复用、收发器、电压兼容、共地、CAN_H/CAN_L 极性和终端电阻等条件。

## Socratic Check

1. 如果 `ip -br link show type can` 完全没有输出，第一反应应该是反复修改波特率，还是检查运行设备树与驱动？答案是后者，因为连网络接口都没有，问题发生在位时序配置之前。
2. `candump` 看到了本机的 `0x2FF` 和 STM32 返回的 `0x2FE`，哪一个更能证明端到端链路成功？答案是 `0x2FE`，因为它要求 STM32 真正接收、解析并生成响应，再把响应送回 K1 Mini。

## Quick Summary
- 一帧数据要依次经过应用、SocketCAN、驱动、CAN 控制器、收发器和物理总线，任何一层未接通都会失败。
- 定制镜像的直接目的，是让运行设备树启用 CAN1 并选对引脚，使驱动能够注册 `can0`。
- `0x101` 证明 STM32 到 K1 Mini 的单向链路；`0x2FF → 0x2FE` 回显证明请求、STM32 软件处理和返回路径都已贯通。
